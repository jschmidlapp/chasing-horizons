# Media pipeline

Photos are **not** stored in git: the originals are about 0.9 GB, and GitHub Pages has a 1 GB site limit.
Cloudflare R2 is the source of truth. Git only holds the small manifest `src/data/media.json`.

## Keys and references

Each image has a **key**, a path like `trips/hike-to-sky-pond/2ebd7ab4be.jpg`. The file name is the first
10 hex digits of the MD5 of the original file, so re-adding the same photo is a no-op. Treat keys as
**opaque IDs**: the folder prefix only records where the photo was first added. Spots moved from
`trips/` still use `trips/...` keys, and that's fine. Never rename keys of uploaded photos; R2 and
the manifest would get out of sync. Content
references images as `/media/<key>`, in Markdown bodies and frontmatter alike.

At render time, `src/lib/media-core.mjs` turns `/media/<key>` into
`<PUBLIC_MEDIA_BASE_URL>/<key minus ext>-<width>.webp` with a `srcset` built from the widths listed in
the manifest. A `/media/…` ref missing from the manifest is passed through unchanged, so plain external
URLs also work.

## Local folders (gitignored)

```
.media/originals/<key>                  source images as imported/added
.media/variants/<key minus ext>-<w>.webp  generated by media:process
```

### How the dev server serves images

Under `npm run dev`, image URLs always point at the dev server, whatever `PUBLIC_MEDIA_BASE_URL` says
(the `local-media` integration in `astro.config.mjs`):

| Request | Served from |
| --- | --- |
| `/_media/<variant>.webp` | `.media/variants/` if the file exists, otherwise a 302 redirect to the same file on R2 |
| `/media/<key>` | `.media/originals/`. This is what a photo looks like after `media:add` but before `media:process` (full size, not responsive) |

So new photos preview locally before anything is uploaded, and a machine with no local copies still
works (everything redirects to R2). `src/data/media.json` is re-read whenever it changes. A page that
was rendered before you ran `media:process` keeps showing the original until you edit and save that page
again (or restart the dev server).

Production builds (`npm run build`, CI) always link straight to `PUBLIC_MEDIA_BASE_URL`.

## Variants

`scripts/media/widths.mjs`: widths 480/960/1600/2400, long edge capped at 2400 px, WebP quality 72.
The current set is about 513 MB for 523 photos. If you change these settings, delete `.media/variants`,
then run `media:process` and `media:upload -- --force`.

## R2 bucket layout

```
originals/<key>      archival originals (lets us regenerate variants on any machine)
w/<variant>          what the site links to; uploaded with Cache-Control: immutable
```

`PUBLIC_MEDIA_BASE_URL` = public bucket URL + `/w`, currently
`https://img.broadcastfrequency.net/w` (R2 custom domain). The bucket's r2.dev URL was only for setup.

## Commands

| Command | What it does |
| --- | --- |
| `npm run media:add -- trips/<slug> files…` | copy photos into `.media/originals` under hashed keys and print Markdown lines |
| `npm run media:process` | create missing variants and rewrite `src/data/media.json` (commit it!) |
| `npm run media:upload [-- --force]` | upload new or changed originals and variants to R2 |
| `npm run media:pull` | download originals from R2 (new machine), then run `media:process` |

## Adding photos to a trip or spot

```sh
npm run dev                                                          # optional: preview as you go
npm run media:add -- spots/calero-county-park ~/Pictures/ride/*.jpg  # prints ![](/media/spots/calero-county-park/…)
# paste the lines into src/content/spots/calero-county-park/index.md (add alt text in the [])
npm run media:process      # WebP sizes + manifest (preview now shows the responsive versions)
npm run media:upload       # only new files are sent
git add src/data/media.json src/content/spots/calero-county-park && git commit && git push
```

Photos uploaded straight to the bucket through the Cloudflare dashboard get no WebP versions and no
manifest entry. If you do that, put them under `originals/<key>` and run `media:pull`, `media:process`
and `media:upload`.

Upload before pushing. Otherwise the deployed page links to variants that aren't on R2 yet.

## Credentials

`.env` (gitignored, template in `.env.example`) needs `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`,
`R2_SECRET_ACCESS_KEY` and `R2_BUCKET`. Create the token in the Cloudflare dashboard under R2 → Manage
API tokens, with **Object Read & Write** on this bucket only.

> Gotcha: the token page shows three values. `R2_ACCESS_KEY_ID` is the 32-character **Access Key ID**,
> not the longer token value that starts with `cfut_`. The token value is optional; keep it as
> `R2_API_TOKEN` for Cloudflare REST API calls. Cloudflare derives the S3 pair from it:
> Access Key ID = the token's ID (`GET /user/tokens/verify`) and secret = SHA-256 of the token value.

CI does not need these; it only needs the public URL (see [deployment.md](deployment.md)).
